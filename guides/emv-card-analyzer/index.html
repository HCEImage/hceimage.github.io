Before starting

  • Use an Android device with NFC enabled.
  • Analyze only cards and test media that you are authorized to inspect.
  • Keep other NFC cards and tags away, and hold the card steadily within the phone's NFC field during analysis.

EMV Card Analyzer reads card data for diagnostics. Payment authorization, PIN/CVM, card authentication and card update commands are outside this workflow. Some cards can still update internal counters when processing GPO.

Your first single-tap analysis

Use a supported contactless EMV test card you are authorized to inspect, such as a Visa or Mastercard EMV card. No external reader, profile import, key entry or payment-terminal setup is needed.

Authorized test cardProvides its supported application data

One NFC presentation

Android phoneEMV Card Analyzer acts as the reader
  1. Prepare the phone. Check NFC status in Settings, open Analyzer and keep other NFC cards away. Stay in Analyzer during the read.
  2. Start and present once. Choose Start analysis, then hold the test card against the phone's NFC antenna. Keep it steady until Completed, Incomplete, Unsupported, Interrupted or Failed appears. One presentation can read more than one supported application; you do not need to tap again for each one.
  3. Review the evidence. Remove the card after the read ends. Review the captured applications, scroll down to APDU exchange and open an entry to inspect its command and response. Use All tags or Diagnostic findings for captured data, then open History for the saved analysis and optional note.

Expected result: Completed means the supported data read finished, not that a payment succeeded or the card is genuine. The app does not ask for a payment PIN or perform cardholder verification. Compatibility depends on the card application and reader; Incomplete can still preserve useful evidence.

Open any screen at full size. These real UI captures use synthetic example data for a single analysis, not a recording of a physical card read. Your card's applications, data and diagnostic findings can differ.

If reading stops: inspect the status and available findings. Check NFC and antenna position before starting a fresh analysis. Do not repeatedly present a card without reviewing the result; processing options can affect internal card counters.

What the read includes

Analyzer discovers applications, selects supported candidates, requests processing options and reads advertised AFL records.

After a successful UnionPay core read, Analyzer also requests additional diagnostic data and reads a valid advertised transaction log of up to ten records. This may extend the read. An unavailable additional object or log record can still leave the core read Completed. If the additional step is interrupted, the completed application data is retained.

Understand the result

Completed means the supported data read finished. Incomplete preserves evidence from a read with unresolved application steps. Unsupported identifies a card technology or application outside the reader scope. Interrupted keeps partial evidence when a read stops or loses communication. Failed provides the available technical reason.

Compatibility varies between cards, devices and application profiles. An incomplete analysis does not by itself establish that a card is invalid.

Inspect APDU and EMV data

Summary names an application using a valid tag 50 from the payment directory, then a valid tag 50 from its SELECT response, then its AID. Payment scheme identifies the family. Product identifies a known AID prefix and appears separately. For card number and expiry, Summary uses the dedicated tags when available and can fill a missing field from valid Track 2 equivalent data.

Open Details beside an application to expand its identity and reading progress. Scroll below the result summary and optional note to APDU exchange. Open an exchange to inspect its raw command and response with contextual decoding of command headers, status words, BER-TLV and DOL fields. When the captured SELECT exchanges establish clear boundaries, the timeline groups APDUs under numbered application headings and keeps the original order and APDU numbers. All tags browses the captured data offline.

For supported D-PAS Issuer Application Data (9F10) layouts with CVN 15 or 16 (hexadecimal), APDU detail and Full reports decode the documented issuer-data fields and card verification results. Unknown variants, reserved fields and opaque issuer data remain identified as unknown. This interpretation does not verify a cryptogram or authenticate the card.

With sufficient UnionPay context, the timeline explains 6F00 for the optional offline spending amount and 6A83 for a missing transaction-log record. The status word stays visible. A missing AFL record can make the core read Incomplete.

Review diagnostic findings

Analyzer checks the captured SELECT, GPO and record evidence for supported applications. Open Diagnostic findings in the result summary to see Error, Warning, Information and Not evaluated observations. A finding can point to the source APDUs and cite the reference procedure. APDU detail shows findings for that exchange.

Finding severity describes the captured evidence. The analysis status describes how far the data read progressed. A Completed result may still contain observations. Missing evidence or checks outside the implemented assessment can appear as Not evaluated.

Supported contactless reading

Analyzer implements a diagnostic subset of each reference procedure. Support depends on the card application, its advertised mode and the Android NFC reader.

Application / procedureReferenceDiagnostic scope
MastercardBook C-2EMV data reading, including supported Maestro, U.S. Maestro and Cirrus applications.
VisaBook C-3EMV data reading, including supported Visa Electron, V PAY, Interlink and Visa U.S. Common Debit applications.
American ExpressBook C-4EMV data reading.
JCBBook C-5EMV and JCB Legacy data reading. The Legacy read ends after the supported GPO and AFL sequence.
Discover / Diners D-PASBook C-6Supported D-PAS applications, including Discover U.S. Common Debit.
Discover ZIPD-PAS Card Application Specification, ZIP procedureSeparate data reading of advertised AFL records and Track 1/2. Optional captured DCVV is not cryptographically verified.
UnionPayBook C-7Core data and bounded additional diagnostics, including supported U.S. Common Debit applications.

Analyzer uses the full AIDs listed by the card. If the payment directory is missing or lists no candidates, it tries a bounded list of AID prefixes. An explicitly unsupported application mode or kernel identifier is recorded with its stop reason.

Discover ZIP is read only when its supported application is advertised by the payment directory; it is not added to the fallback list. It follows its own SELECT, GPO and AFL-record procedure, rather than claiming to execute Book C-6. Completed requires all advertised records and correctly encoded Track 1 and Track 2 with consistent card identity and expiry. Invalid optional DCVV data can leave the read Incomplete; captured DCVV is not cryptographically verified.

JCB Legacy and Discover ZIP are bounded data reads, not complete legacy payment flows. ZIP does not reconstruct tracks or send checksum, GENERATE AC, PIN or card-update commands. Historical C-1, other legacy/magstripe procedures and external contact readers remain outside the reader scope.

Understand Card response timing

Card response measures the exchange through the NFC reader, including device overhead. A recorded duration can also describe an unsuccessful exchange. History Duration spans card detection through the final result. Time spent waiting for a card is excluded. History and reports show Not recorded when timing is absent.

Keep results while moving between screens

Switching tabs, backgrounding the app or rotating the screen stops NFC reading without restarting it automatically. The live result stays available while the app process remains alive. Start replaces it. Saved History is independent of this temporary workspace.

Use history, reports and traces

New analysis traces use envelope schema 1 and payload.schemaVersion: 2. Analyzer also imports schema 1 traces with Full evidence. See the trace reference for the structure and compatibility rules.

History stores analysis snapshots and optional notes locally. Filter by result, delete a record with Undo, or clear History after confirmation. Completed entries show their captured application count. Incomplete discovery can leave the count unknown, so other outcomes show a dash.

From a saved result, choose Export for a readable Markdown, HTML or PDF report or a portable JSON trace. Choose History → Import to preview a trace. Inspect Summary, including any saved note, or APDU exchange. Choose Save to history to keep the record or Back to discard the preview.

Traces contain full evidence, including captured APDUs, decoded card data and notes. Report offers Full evidence and Redacted. Redacted reports omit card-derived values and notes and keep timestamps, scheme, APDU headers, status words, timing and available findings. Review the file before sharing it.

A .hceimage.json trace identifies itself as com.hceimage.diagnostic / emv-analysis. It is a recorded diagnostic result, not an HCE card profile.

Analysis-trace specification

Configure Analyzer and History

Settings shows NFC status and offers a shortcut to Android NFC settings. Keep screen on and Stop analyzer after result are on by default. The optional Start timeout applies while waiting for a card. History retains the newest 100 saved records by default and can keep 500, 1,000 or all records. Tag reference and APDU response codes are available offline.

Use the information icon on Analyzer, History or Settings for guidance specific to that screen. This guide describes reading, reviewing evidence, history and configuration. The separate analysis-trace specification covers file structure and import compatibility; it supplements rather than replaces the workflow guide.

Handle captured card data carefully

Analyze only cards you are authorized to inspect. Summary masks the card number until you reveal it. APDU details, decoded tags, clipboard copies and Full evidence exports can still expose captured values. Choose a Redacted report to omit card-derived values and notes. Review the remaining context before sharing a screenshot or diagnostic file.

Logcat detail defaults to Sessions in the Google Play app. APDUs adds raw commands and responses that can contain sensitive card data. History stays on the device and is excluded from Android backup and device transfer. Clearing History leaves exported files, clipboard copies and system logs in place.
