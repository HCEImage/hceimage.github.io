HCE Test Tool

Test contactless terminal flows with synthetic card profiles

Android · HCE Test Tool 1.0.0

Use Android host card emulation to present a selected test profile, inspect the APDU exchange and review the resulting flow in one place.

Built-in profile catalog

The catalog contains 24 Built-in profiles with 43 Test guidance scenarios: seven Visa, five Mastercard, seven American Express and five JCB profiles. Visa separates Adaptive CVM, Online PIN, Signature, No CVM, physical Magstripe and mobile EMV/Magstripe. Mastercard separates physical Online PIN, No CVM / Signature and Magstripe from mobile EMV/Magstripe. American Express separates physical Adaptive CVM, No CVM / Signature, No CVM and Magstripe, plus Mobile EMV, Mobile EMV without CDA and Mobile Magstripe. JCB provides five selected physical EMV/Legacy scenarios.

Open each profile’s Test guidance for reader capabilities, amount conditions, a documented Test/Reference PIN and known limits. Visa Online PIN and Signature are fixed requests, including low-value transactions; Adaptive CVM follows reader capabilities and the CVM-required setting. Amounts alone do not select a reader capability. A No CVM profile above the reader limit or a successfully read Magstripe profile can still be rejected by reader policy.

Eligible mobile EMV profiles separately explain the pre-verified baseline and optional simulated two-presentation verification. It is not real device authentication or wallet provisioning; Magstripe and JCB profiles do not gain interactive verification. Successful card-side checks are not payment approval or host acceptance.

Mastercard Online PIN requires a reader advertising Online PIN at the chosen amount, even below its CVM limit. Contactless Magstripe requires reader and payment-application acceptance of the legacy entry mode; above-limit terminal PIN and unverified-device-CVM retry are different paths. Mobile PIN references remain in Test guidance, not on the selected profile card. Reset restores the selected profile’s embedded security defaults without changing the saved profile.

Before starting

  • Use an Android device with NFC host card emulation support and NFC enabled.
  • Use only an authorized external contactless reader or payment terminal configured for testing.
  • Keep the test host and terminal configuration available when interpreting authorization or kernel-specific behavior.

HCE Test Tool contains synthetic test card data and is intended exclusively for development, integration testing and controlled test environments. It cannot perform real payments.

Run a test

  1. Open Change on the Card profile card. The picker starts with All; optionally filter by payment brand and select a profile. A second row below the brands filters by All / Built-in / Imported / Created. Both filters combine; browsing or dismissing the picker does not change the active profile or result. Picker cards match the Card profiles catalog, including complete wrapping descriptions, origin and readiness chips, and highlight the current selection. Profiles with warnings remain selectable; profiles with validation errors are excluded.
  2. Review the profile summary and open Test guidance in its separate footer for profile-specific expectations. The information action beside Card profile opens general Emulator guidance.
  3. For a physical profile, a documented PIN for an Online PIN or terminal-dependent scenario appears simply as PIN below PAN on the selected profile card. Reference PINs for No CVM, Signature, on-device CVM and Not applicable remain in Test guidance only. If relevant scenarios use different PINs, the card shows See Test guidance instead. Enter a test PIN only when the test terminal requests it; it is not a device unlock code.
  4. The reviewed Visa Mobile EMV scenario indicates already-confirmed device CVM, so any reference PIN remains in guidance only. Mobile form factor alone does not determine CVM: other profiles may retain reader-dependent fallback behavior. Re-import an updated custom definition to replace its older guidance metadata; existing imports are not silently rewritten.
  5. If the authorized test host requires different test credentials, choose Test configuration → Test security data → Change. Profile defaults remain unchanged when no override is applied. Only the explicit Change buttons open profile/security selection; the card bodies are not clickable. Simulated device CVM changes through its switch.
  6. Start emulation and present the Android device to the reader or terminal.
  7. Keep the device in position until the application reports a completed, failed or interrupted outcome.

Inspect the exchange

The live timeline records commands and responses as the terminal communicates with the selected profile. Open an entry to inspect the raw APDU together with contextual command headers, status words, BER-TLV data, DOL values and recognized payment-scheme tags. Command/response timings and session duration help locate delays; they do not measure the terminal's complete payment processing time.

The result view compares the observed exchange with the expected profile flow. A failed or interrupted result is diagnostic context, not by itself proof of a terminal defect: reader configuration, terminal kernels and processing outside the emulator can affect the outcome.

Profile cards use neutral surfaces. History list cards match the recorded profile-check report: blue for passed checks, amber for interrupted checks and red for failed checks. A negative scenario may still pass its checks. Without recorded checks, the session outcome supplies the fallback color. In the detail, status, times and metadata stay neutral above the separate colored report. Read the result and report explanation, not color alone. Passed checks do not mean payment approval.

Use history and reports

Completed, failed and interrupted attempts are kept locally. History filters help isolate an outcome, while session details preserve validation checks, the APDU timeline and optional test notes. Delete a single record or clear history when it is no longer needed. Diagnostic reports can be saved or shared in Markdown, HTML or PDF when an integration result needs to be reviewed outside the application.

Choose Full evidence for captured values or Redacted to retain structural diagnostics while omitting card-derived values and notes. Redacted is not a guarantee of anonymity: review the retained diagnostic context before sharing either form. Single-record deletion offers Undo. Settings controls history retention, appearance, Logcat detail, result vibration and emulation timeout. High-detail logs and Full evidence reports can contain synthetic card data; review them before sharing.

Keep results while moving between screens

Switching tabs, backgrounding the app or rotating the screen stops NFC emulation without restarting it automatically. The live result stays available while the app process remains alive. Start replaces it; selecting a different profile clears it. Merely browsing brand filters does not change the active profile. Saved History is independent of this temporary workspace. Applied security overrides survive tabs and rotation, but an unfinished editor draft is discarded when its screen is recreated.

Handle test security data carefully

Only explicitly authorized test values belong in Test security data. Values entered in the Emulator are masked by default, validated before use and retained in memory only. Apply validates and activates the draft; Cancel discards unapplied edits. Reset asks for confirmation, then immediately removes that profile’s overrides and draft, restoring its own defaults or synthetic engine defaults when none are supplied. It never changes the saved profile.

Temporary overrides clear from the next-run selection after the next emulation with that profile starts unless you choose Keep until the app is closed. The active session still uses its captured values; its result and history retain the source used for that session. The Emulator security card describes the next run when no session is active. Overrides are not written to card profiles, history, reports, logs, clipboard output or backups; generated test APDU responses can appear in history and reports. Separately, synthetic defaults included in an imported profile persist with that profile file. Never enter production issuer keys.

Simulate device verification

Eligible Visa qVSDC, Mastercard Mobile EMV and Amex mobile EMV profiles offer Simulated device CVM in Test configuration. Off preserves the existing pre-verified synthetic scenario. With On, start emulation, present the phone and remove it when the reader requests verification. Cancel and Continue replace Start side by side in the main action area, outside configuration. Continue becomes available after removal and confirms the simulation while arming the second presentation in one action. Present the phone again; no additional Start is needed. Reader support is required; no biometric prompt or real wallet authentication is performed. For Amex, use the application keyset even on its magstripe paths; changing only application keys can correctly show Mixed when offline authentication still uses profile defaults. Reset restores the profile defaults.

The animated status card guides both taps. Profile, security and simulation controls remain locked while running or awaiting Continue; no partial report, note or APDU list is shown. Stop before any APDU returns to Emulation is off without creating history. The first verification request checkpoints one scenario as Awaiting verification. Continue adds the second presentation to that same record. The live report, history card and detail agree on the overall outcome: Completed (blue), Interrupted (amber), or Failed (red). Passing first-tap checks alone never completes the scenario or proves payment approval.

Cancel, expiry, leaving the app, or Stop before a second-tap APDU retains the first evidence as Interrupted. One shared note follows the final report; History details and Full/Redacted exports separate First tap and Second tap with their original numbering and independent checks. On restart, unfinished checkpoints become Interrupted without rearming NFC. Existing ordinary history and notes remain supported. Live and saved First tap / Second tap headings include the same APDU counts. Full exports include the shared note. Redacted exports omit the note, card-derived values and presentation identities. These are local history changes, not a native profile-format revision.

Continue must occur within two minutes of completion of the first request and does not extend that window. Expired/cancelled verification, changed profile/security bindings and repeated Continue actions never silently start a fresh first presentation. Stop, Cancel, profile/security changes, leaving the Emulator, backgrounding or rotation cancel pending verification. Use Keep until app closed for custom security data that must remain identical across both presentations. History retains one scenario with separately bounded presentations, not payment approval. Standalone Visa MSD, Mastercard MSI and JCB interactive emulation are not implemented.

Import a card profile

Choose Card profiles → Import to open a native .hceimage.json definition. Review the preview before saving it. The file identifies itself as com.hceimage.definition / card-profile; the app validates its profile schema, unique Profile ID, supported brand, AIDs, APDU behavior and supplied test security data. Built-in profiles cannot be replaced or deleted.

Payload schema version identifies payload.schemaVersion in profile detail and import preview. Current definitions and downloads use payload schema 3 inside envelope schema 1; payloads 1 and 2 remain readable without rewriting them. Schema 3 includes selected JCB EMV/Legacy support, response states, personalized Visa application keys, adaptive CVM and compatible Amex CDA templates. Optional Visa MSD/Mastercard MSI per-card keys remain supported. The legacy-security reference explains key roles, KCV checks and temporary overrides.

Imported and Created profiles appear alongside Built-in profiles and can be isolated with the Profile source filter. Swipe a user-owned card or use Delete in its detail; both routes provide Undo. Deleting a profile does not delete its existing session history; repeating a saved session requires an available profile with the same Profile ID. Profile-default synthetic test security data persists with that private profile. Values you apply later in the Emulator are temporary overrides and do not change the profile file. Keep original import files for re-import after reinstalling or changing devices.

Copy and manage your profiles

Profile source uses the same labels on cards, in filters and in detail: Built-in, Imported and Created. These library labels describe how the app obtained a profile; they are separate from the optional provenance metadata inside its JSON.

  1. Open an existing profile in Card profiles and choose Copy.
  2. Enter a name and a unique Profile ID, review the preview and choose Create. Cancel leaves the original unchanged.
  3. Select the new Created profile in the Emulator when you want to test it.

Functional data and profile security defaults remain intact. The copy replaces provenance with "source": { "format": "CUSTOM" } and does not copy temporary Emulator overrides. Copy edits identity metadata only; it does not edit PAN, AID, tracks or certificates. Built-in profiles are protected; Imported and Created profiles can be deleted with Undo. Native profile export and an editor for emulation values are not currently available.
