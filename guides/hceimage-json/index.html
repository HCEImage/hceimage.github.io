Import and test on a terminal

  1. Download a JSON file to your Android device. In HCE Test Tool, choose Card profiles → Import, select it, review the metadata and confirm. Each example has a separate Profile ID from the bundled catalog. The downloads use envelope schema 1 and require support for card-profile payload schema 3.
  2. Select the imported example in the Emulator and open its Test guidance. Visa and Mastercard Online PIN request PIN at both test amounts, so the reader must advertise Online PIN even below its CVM limit. Amex Adaptive CVM has below-limit No CVM and above-limit Online PIN preference with reader-dependent fallback. For CZK with a configured 500 CZK CVM limit, use 10 CZK and 550 CZK; amounts alone do not select capabilities. The Visa example's Test PIN is 123412; Mastercard, Amex and JCB use 1234. The JCB example documents an above-limit Online PIN purchase: start with 550 CZK and matching JCB reader capabilities. HCE Test Tool does not verify the PIN: the configured test host determines the outcome.
  3. Enable the matching brand and AID on an authorized test terminal. Configure its test card/BIN table for the example PAN and, if it verifies cryptograms, configure the host simulator with the demonstration keys and matching derivation settings.
  4. Start emulation before presenting the phone. The terminal builds PDOL/CDOL data and chooses its own command flow; inspect the APDU timeline and the terminal result separately. Use the structured Test PIN row only when the terminal requests PIN; it is not a phone unlock code.

These profiles support meaningful terminal read flows, but are not certified scheme test cases or a guarantee of compatibility with every kernel. Card/BIN routing, CVM settings, offline-authentication configuration and host processing remain outside the emulator. In particular, an Amex UNKNOWN_CARD rejection can be a payment-application configuration issue even after a completed APDU exchange. A completed HCE session is not proof of payment approval.

Import rejects duplicate Profile IDs. To replace a previously downloaded example, explicitly delete that imported snapshot and reimport after the deletion completes, or give a separate copy a new unique ID. Renaming the filename does not change its ID. These are physical examples: their documented Online PIN appears on the selected profile card; mobile-profile PIN references follow the separate guidance-only policy.

The downloads include persistent synthetic security defaults. Test security data overrides are temporary; use Keep until app closed only for intentional reuse. Reset returns to this imported profile’s defaults without changing its saved JSON. Mastercard can correctly show Mixed when only the application key is customized and offline authentication still uses profile keys. Amex and JCB use their application MK-AC group, not Visa/MC legacy-key controls. For JCB CDA, keep the matching ICC key/certificates; changing only application keys can also show Mixed.

Public test keys and safe editing

"testMasterKeyAc": "0123456789ABCDEFFEDCBA9876543210",
"testMasterKeyAcKcv": "08D7B4"

Excerpt inside the crypto group, not a standalone import file. This intentionally public demonstration key provides no secrecy and is only a syntax illustration; use the key role, values and KCV actually declared by the selected download.

Use each file’s own synthetic defaults and matching KCVs. Mastercard application overrides require both MK-AC and MK-IDN plus matching PAN/sequence-number inputs. Visa uses the key role declared in its crypto group; a personalized UDK-AC must never be combined with MK-AC. Amex uses MK-AC even for its supported contactless magstripe paths. JCB uses MK-AC and its matching diversification PAN/sequence number, with no MK-IDN or Visa/MC legacy card-key group. ICC keys must match the included certificates. Defaults persist with the imported file; Emulator overrides are separate temporary values. Never substitute production credentials.

  • To keep a second edited copy, change payload.id to a new lowercase, hyphenated Profile ID. Changing the filename alone does not avoid duplicate-ID rejection.
  • When changing a PAN, update every associated PAN/Track 2 value and keep the check digit valid. Signed test certificates can also bind the PAN: do not independently edit a profile's PAN, RSA material or certificates without rebuilding all dependent authentication data.
  • When changing an AID, label or EMV value, also update related response TLVs and lengths. Changing application metadata does not rewrite APDU responses automatically.
  • When changing a key, recompute its supplied KCV and update the test host configuration. Keeping an old KCV deliberately causes import rejection.

Importable JSON cannot contain comments. Unknown payload fields such as _comment, optional or mandatory are also rejected. This field reference supplies the annotations without breaking the downloads; use the supported description and testScenarios fields for guidance inside the file.

The shared envelope

Both document types use the .hceimage.json suffix and four top-level fields. Applications check the contents, not just the filename.

FieldMeaning
formatDocument family: a reusable definition or a diagnostic result.
schemaVersionShared envelope schema, independent of the app release and payload schema.
kindSpecific payload type within the family.
payloadJSON object interpreted by the appropriate application.

The envelope schema number does not describe the contents of payload. A consumer must check the expected format and kind, then validate the payload under its own schema. The envelope does not authenticate a file or guarantee that its data is safe.

Field types matter: format and kind must be JSON strings, schemaVersion must be an integer number rather than a quoted number, and payload must be a JSON object. Missing, null or incorrectly typed required fields are rejected. Additional envelope fields are ignored, but the application still validates its specific payload.

Card-profile definition

HCE Test Tool imports a native, reusable synthetic card profile. Its envelope uses format: com.hceimage.definition and kind: card-profile. The profile schema is in payload.schemaVersion.

{
  "format": "com.hceimage.definition",
  "schemaVersion": 1,
  "kind": "card-profile",
  "payload": {
    "schemaVersion": 3,
    "id": "example-profile",
    "name": "Example profile"
  }
}

Structure illustration only: this omits required profile fields and cannot be imported as-is.

Two independent schemas: the shared envelope uses schemaVersion: 1; current card profiles and downloads use payload.schemaVersion: 3. Import accepts payloads 1, 2 and 3. Older files retain their own schema on import and Copy. Payload schema version in profile detail and import preview refers to the inner value, not the envelope or application release.

Payload 3: selected JCB EMV/Legacy scenarios, optional APDU response states, personalized Visa CVN22 application keys, adaptive reader-dependent CVM and compatible Amex first-GAC CDA templates share this version. New definitions use payload 3 consistently. Payloads 1 and 2 remain readable; a reader that supports only an older version may reject new downloads. Changing the version number alone does not implement new behavior.

Payload fieldPurpose
id, name, descriptionStable Profile ID and nonblank display text. IDs contain 1–64 lowercase letters, digits or hyphens, starting with a letter or digit, and must be unique in the library. Names contain at most 120 characters.
brand, formFactor, technologiesPayment brand, intended physical/tokenized test-card scenario and contactless processing paths. Form factor is separate from profile origin and CVM; a confirmed CVM result alone does not establish tokenization. All downloadable profiles are synthetic, not provisioned wallets.
applications[]AIDs and application settings, including optional profile-default test security data in crypto or schema-2 legacyCrypto.
apduRules[], expectedFlow[]APDU request/response behavior and rule IDs expected during validation.
initialState, apduRules[].response.requiredState, apduRules[].response.nextStatePayload 3 only. Optional per-emulation state and response guard/transition. Names use 1–64 ASCII letters, digits or underscores and start with a letter; guards must be reachable from the initial state. A guard mismatch returns 6985 without changing state; a transition applies only after a successful 9000 response. Starting a new emulation restores the initial state. This is not persistent card risk, key storage or a way to implement a new payment scheme.
applications[].crypto.testCardKeyAc, testCardKeyAcKcvPayload 3, Visa CVN22 only. Optional personalized 16-byte hexadecimal test application key, with an optional matching three-byte KCV. Use it instead of, never together with, testMasterKeyAc and its KCV. It directly derives the session key without repeating PAN/sequence-number diversification. The security editor labels it UDK-AC, keeps profile PAN/sequence number fixed and applies the usual temporary override/Reset behavior. Legacy MSD/MSI legacyCrypto.testCardKey is a different group. Use synthetic keys only.
testScenarios[]Optional terminal setup, CVM and expected-outcome guidance; it does not drive the terminal or host.
sourceOptional development provenance, not a signature or authenticity claim.

A complete payload needs at least one application and one APDU rule. Each applications[] entry has an aid, optional label/PAN/DOL and CVM settings, and an optional crypto group. The supported dynamic cryptogram groups identify their algorithm and synthetic test keys; optional three-byte KCV values are checked against the corresponding keys. Empty or partial security-data groups are not silently completed from other profiles.

Each apduRules[] entry gives an ID, a command matcher (request), a fixed or templated response, and an outcome. expectedFlow[] refers to those IDs. testScenarios[] may describe transaction amount conditions, expected CVM, a Test PIN and terminal setup, but those instructions do not execute a transaction. In-app import accepts supported Visa, Mastercard, American Express and JCB profiles only and checks the primary AID, brand and cryptogram algorithm together.

Test PINs: in payload 1/2, testPin/pinNote belong to Online PIN scenarios. Payload 3 also accepts a substantiated reference PIN for other CVM scenarios. Test guidance presents it separately below Expected CVM; the short usage note does not repeat the numeric value: "Use only if the test terminal requests PIN. This value does not change the expected CVM and is not a device unlock code." A documented test-plan default must be distinguished from a PIN contained in the profile source. Use only substantiated synthetic test values. The terminal/test host, not HCE Test Tool, verifies online PINs. The payload-3 downloads below carry structured PIN references and profile-specific Test guidance.

Profile guidance: the refreshed built-in catalog has 24 profiles and 43 scenarios. All seven Visa, five Mastercard, seven American Express and five JCB bundled definitions use payload 3. Amex separates physical EMV/magstripe and mobile EMV with or without CDA/magstripe; both mobile EMV profiles include optional simulated two-presentation guidance. The independent envelope remains v1. Guidance explains expected behavior but does not execute CVM or change a profile’s APDU/cryptographic rules. A copied profile must have a new unique ID; retired built-in IDs do not cause user-owned imports or history to be deleted. The four downloads are complete physical examples derived from this catalog, with distinct IDs and their own embedded guidance.

Adaptive CVM: Visa CVN22 may use cvmPolicy: VISA_ADAPTIVE_CVM. The {{VISA_CTQ}} response token requests no CVM below the reader's CVM-required setting; when required, it prefers supported Online PIN, then supported signature, otherwise returns no card CVM request. Use the token in GPO and 9F69. The fDDA signer uses the same CTQ in the last two bytes of its seven-byte authentication data, preserving the first five bytes. This is bounded synthetic behavior, not a general card-risk engine, successful terminal CVM verification or payment approval. Fixed Online PIN, Signature and No CVM profiles keep their distinct requests; do not infer their policy from the amount alone.

  1. Prepare a complete UTF-8 native definition of at most 1 MB with synthetic test values only. Start with a downloadable example or use a bundled profile as a structural reference.
  2. In HCE Test Tool, open Card profiles → Import and select the file.
  3. Review the preview, warnings and Profile ID, then confirm. Invalid structure, unsupported brands or duplicate IDs block import.
  4. Select the imported profile in the Emulator and review its Test guidance before starting a controlled NFC test.

Test security data embedded in a profile persists with its private imported file. Values entered later in the Emulator are separate in-memory overrides and do not edit that file. Keep the original for re-import; imported profiles are excluded from Android backup. Never use production keys or real payment credentials.

Legacy per-card cryptography

Payload schema 2 adds optional applications[].legacyCrypto for Visa MSD and Mastercard MSI. This group is separate from EMV crypto; the two groups cannot coexist in one application. Its algorithm must match the brand and a MAGSTRIPE_CONTACTLESS flow. Schema-1 profiles cannot contain this group.

"legacyCrypto": {
  "algorithm": "VISA_MSD_DCVV",
  "testCardKey": "0123456789ABCDEFFEDCBA9876543210",
  "testCardKeyKcv": "08D7B4"
}

Excerpt for a complete Visa MSD application, not a standalone import. For Mastercard MSI use MASTERCARD_MSI_CVC3. The public demonstration key provides no secrecy.

testCardKey is a mandatory personalized 16-byte, two-key TDES synthetic card key, not an issuer master key. Optional testCardKeyKcv is six hexadecimal digits and must match the first three bytes of TDES encryption of a zero block. Import checks the key, brand, PAN/track consistency and required command inputs; an empty or incomplete group is rejected.

Visa MSD generates three decimal dCVV digits and uses the rightmost four decimal ATC digits. Mastercard MSI generates binary Track 1/2 CVC3 from the track templates read in that transaction, the UDOL unpredictable number and binary ATC; the reader inserts decimal results into its tracks. Terminal and test-host configurations must support the selected flow and matching synthetic keys.

In Test security data, leave the controls unchanged for profile defaults, enable Custom legacy cryptography key for a complete temporary card-key replacement, or use Fixed legacy verification results for deliberate test values. Custom-key and fixed-result modes are mutually exclusive. Fields are masked; summaries expose KCVs, not keys. Older profiles without legacyCrypto keep scripted results.

American Express AEIPS uses its existing crypto MK-AC group for CVN 01 EMV and CVN 02 magstripe. The selected GPO AIP and returned CDOL1 determine the branch; the response IAD reports the same CVN and CVR used in cryptogram generation. Do not add a Visa/MC legacy-key group to an Amex profile. If only application keys are customized, Mixed can correctly indicate that offline authentication still uses the profile ICC key. Reset restores the profile defaults, not a rewrite of the saved JSON. These are synthetic test implementations, not real wallet provisioning or certification.

The payload-3 implementation supports {{AMEX_SDAD}} for requested first-GENERATE-AC CDA in compatible format-77 profiles. It uses the existing synthetic crypto.testIccPrivateKey group and matching certificates, never private CA or issuer keys. A deliberately no-CDA profile does not fail merely because it omits CDA. Follow the active CDOL rather than an AIP bit alone when selecting the Amex cryptogram path. This does not add issuer scripts, second GENERATE AC or production-wallet support; the downloadable profiles use the matching payload-3 profile contracts.

Mobile Magstripe profiles can explicitly declare optional GET DATA 9F36 with 9F3602{{ATC}}. It reads the current presentation counter after successful GPO without advancing it; later GENERATE AC uses the same value. This does not enable arbitrary GET DATA tags or change the payload version. A physical Amex CVN02 compatibility path can be processed as EMV by a reader when its retained AIP permits it; the reader mode label alone does not select the cryptogram algorithm. Existing imported files are not silently rewritten.

EMV analysis trace

Trace compatibility: EMV analysis trace export uses envelope schema 1 and trace payload schema 2. Import also accepts schema 1 files with Full evidence.

EMV Card Analyzer exports a captured diagnostic result for later inspection. Its envelope uses format: com.hceimage.diagnostic and kind: emv-analysis. The trace schema is in payload.schemaVersion; producer.versionName records the creating app release, not the document schema.

{
  "format": "com.hceimage.diagnostic",
  "schemaVersion": 1,
  "kind": "emv-analysis",
  "payload": {
    "schemaVersion": 2,
    "producer": {
      "applicationId": "com.hceimage.emvcardanalyzer",
      "versionName": "<producer-app-version>"
    }
  }
}

Structure illustration only: an importable trace also needs the result, timing, APDU exchanges and application data.

Schema 2 requires payload.schemaVersion: 2 and carries full evidence. The importer rejects evidence and payloadVersion in schema 2. Schema 1 import requires evidence: "FullEvidence" and accepts payload.schemaVersion: 1 or the legacy payload.payloadVersion: 1. If both schema 1 fields appear, they must be equal JSON integers. The importer rejects Redacted trace files before preview.

Payload fieldPurpose
producer, originCreating application information and original analysis origin; neither proves authenticity.
startedAtEpochMillis, completedAtEpochMillis, result, detailAnalysis times and final outcome.
applicationLabel, scheme, cardInterface, noteSummary and user context.
exchanges[]Ordered APDU commands and responses, context, optional errors and timing.
applications[]Discovered applications, read status and decoded facts linked to APDUs.
diagnosticsOptional assessment with assessmentVersion: 1 and items[].

Each exchanges[] item records command and optional response as APDU hex, scheme, aid, pdol, cdol1 and label. Optional transportError and processingError describe local errors. durationMillis is the recorded card-response timing when available.

Each applications[] item records aid, label, scheme, detail, selected, processingOptionsRead, advertisedRecords, recordsRead, an optional directoryLabel and facts[]. A fact carries tag, name, value and sourceApdus. Each source number must refer to an exchange in the trace, numbered from 1, and can appear only once per fact. Locally generated facts can use sourceApdus: [].

Full evidence may include applications[].product. The importer derives the displayed product from the retained AID. Scheme values include Jcb, Discover and UnionPay. Older importers also need to recognize the scheme values used by the file.

Each diagnostic item records its code, severity, scheme, zero-based applicationIndex, location, reference and sourceApdus. Tag and length fields are optional. The assessment carries observations without card values.

Import validates identifiers, final result, timestamps, APDU framing, collection bounds and schema-specific fields before showing the preview. In JSON, Partial and Error are displayed as Incomplete and Failed in the app.

  1. Open a saved analysis in History → Export → Trace, then save or share the file.
  2. On another installation, choose History → Import. Summary shows any note from the file. Choose Save to history to keep the record or Back to discard the preview.

Trace files can include sensitive card data and notes. Choose a Redacted report for sharing with card-derived values and notes omitted. Previously saved Redacted imports remain available in History for inspection and Redacted report export.

Compatibility boundary

The shared envelope uses schema 1. Current exports use independent payload schemas: 3 for HCE card profiles and 2 for EMV traces. The legacy payload.payloadVersion alias applies to EMV schema 1 Full evidence imports. An analyzer that supports only trace payload schema 1 cannot open exported schema 2 traces.

These files cannot be exchanged between the two importers: HCE Test Tool does not import analysis traces, and EMV Card Analyzer does not import card profiles. Renaming a file does not convert it. A profile definition is an input for controlled emulation; an analysis trace is an output from a recorded NFC read. Neither file is a payment credential, approval record or certification result.
